# FINDER — PHASE 4 DEVELOPMENT NOTES
## Local Library Cache & Intelligent Two-Way Synchronization

**Date:** October 7, 2026  
**Project:** Finder Add-on / Finder Skin  
**Status:** Proposed architecture — approved for feasibility investigation, not yet implemented  
**Primary Objective:** Provide Kodi-library-like browsing responsiveness while retaining synchronization with the user's selected online tracking provider.

---

## 1. OVERALL OBJECTIVE

Develop a lightweight, Finder-managed local library cache that stores the user's relevant media information directly on their Kodi device.

The intention is to substantially reduce unnecessary cloud requests, improve widget loading speeds, and provide a responsive interface on devices with limited RAM and processing resources.

Target devices include:

- Sony Bravia Google TV
- Fire TV Stick
- Fire TV Cube
- MacBook running Kodi
- Other Kodi-compatible devices

**Core design philosophy:**

Browse locally, update immediately, synchronize intelligently, and never interrupt normal viewing unnecessarily.

This feature should be investigated before attempting full Kodi native-library integration.

## 2. LOCAL CACHE ARCHITECTURE

Finder will maintain its own persistent local database inside its Kodi add-on data directory.

The cache should contain relevant information for the user's selected tracking provider, including:

- Watched movie and television episode history
- Resume positions and playback progress
- In Progress and Next Up information
- Watchlists
- Collections
- Personal lists, where supported
- Relevant media metadata and identifiers
- Synchronization timestamps and pending local changes

The cache should use a lightweight database solution, with SQLite as the initial candidate.

It must remain independent of Kodi's native video library database.

Media information should be organized by stable identifiers such as TMDb, IMDb, TVDb, and provider-specific IDs where appropriate.

The database must support safe upgrades and schema migrations without losing existing user information.

## 3. KODI STARTUP BEHAVIOR

**This is one of the highest-priority requirements.**

When Kodi starts:

1. Finder opens its existing local cache.
2. Home screen widgets populate from locally available data.
3. Watched indicators, resume positions, collections, and watchlists appear without waiting for cloud synchronization.
4. Finder checks whether background synchronization is due.
5. If required, synchronization begins quietly after startup, subject to resource availability.
6. Only affected widgets refresh when updated information becomes available.

The objective is to make the Finder home screen feel as responsive as a Kodi native-library interface.

No cloud connection should be required simply to display previously cached content.

Actual loading speed must be benchmarked on target hardware rather than assumed to match Kodi's native library.

## 4. LOCAL CHANGES AND IMMEDIATE FEEDBACK

When a user performs an action, Finder should update the local database immediately.

Examples:

- Marking an episode watched
- Marking a movie unwatched
- Resuming playback
- Completing playback
- Adding or removing an item from Watchlist
- Adding or removing an item from Collection
- Modifying a supported personal list

The visible interface should reflect the change immediately.

Finder records a pending synchronization operation for each locally modified item.

These pending operations remain available until successfully synchronized with the tracking provider.

The design must prevent duplicate operations and preserve pending changes across Kodi restarts.

If a provider does not support a particular operation, Finder must not falsely indicate that it has been synchronized.

## 5. INTELLIGENT TWO-WAY SYNCHRONIZATION

Synchronization must operate in both directions:

**Local Finder → Cloud Provider**

Upload pending local changes, including watched states, resume positions, and list modifications where supported.

**Cloud Provider → Local Finder**

Retrieve remote changes and update corresponding local records.

The system should avoid downloading or uploading complete datasets when incremental operations are available.

Synchronization should use:

- Provider-supported incremental updates
- Last-modified timestamps or change tokens where available
- Local pending-operation tracking
- Batch requests where supported
- Reliable conflict detection and reconciliation
- Safe retries following connection failures

Important: A remote comparison may still require API requests. Finder cannot assume that unchanged local data means no changes occurred online.

For providers without reliable incremental endpoints, use appropriately scheduled or paginated reconciliation.

## 6. AUTOMATIC SYNCHRONIZATION

The initial proposed default is:

**Every six hours while Kodi is running.**

Potential settings:

- Every 6 hours
- Every 12 hours
- Every 24 hours
- Overnight, when Kodi is running
- Check for overdue updates at Kodi startup
- Manual synchronization

These are proposed options, not finalized implementation settings.

Automatic synchronization should be performed by a lightweight background mechanism, without blocking navigation or playback.

Kodi must be running for the normal add-on synchronization mechanism to execute.

If Kodi is closed during a scheduled synchronization period, the operation should become eligible when Kodi next starts.

An initial full synchronization will still be required when the cache is first created or rebuilt.

## 7. EXTENDEDINFO — MANUAL SYNC

Reuse the existing **Sync** function in Finder's ExtendedInfo panel as the user-facing manual synchronization control.

The existing implementation must first be inspected to determine what it currently supports.

The proposed behavior is:

1. User selects Sync.
2. Finder examines pending local changes.
3. Finder uploads supported changes to the selected tracking provider.
4. Finder retrieves relevant remote changes.
5. Finder reconciles local and remote information.
6. Finder updates its local database.
7. Affected widgets and indicators refresh.
8. Finder displays a concise completion or failure notification.

Manual and automatic synchronization must share the same underlying engine.

Do not implement separate synchronization logic for each entry point.

## 8. API RATE-LIMIT PROTECTION

This requirement is particularly important for free-tier accounts.

Finder should minimize unnecessary API requests and respect each provider's documented restrictions.

Recommended protections:

- Provider-specific rate-limit handling
- Batch operations when supported
- Incremental requests instead of full downloads
- Avoidance of redundant requests
- Backoff when rate limits are approached or exceeded
- Respect for server-provided retry intervals
